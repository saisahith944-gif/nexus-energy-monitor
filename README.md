# Nexus Energy — Smart Building Intelligence

A Flask application for monitoring monthly electricity readings room by room across a multi-floor building. The Nexus Energy interface compares manually entered readings with configurable limits, identifies unusual use, and records alerts. It is a demonstration application: no real smart meters or IoT devices are connected.

## Problem statement and objectives

Building administrators need a simple way to spot rooms whose electricity use is approaching or exceeding a reasonable baseline. WattWatch stores readings and historical averages, highlights rooms needing attention, and provides estimated costs and inspection suggestions. A high reading is an indicator to investigate, not proof of electricity wastage.

## Features

- Responsive dark energy command dashboard for three seeded floors and fifteen sample rooms, with a sustainability header, live API status, sound controls, alerts, and a functional navigation rail.
- Interactive CSS-rendered, architectural/isometric building model showing the 15 configured rooms across three floors; each room opens its saved details, the selected room is highlighted, floor focus controls update the model, and status colors come from current database readings.
- Illustrated, interactive top-down floor plans in Building Map show each demonstration room, a floor corridor, furnishings, and live status/usage; room selection opens the existing room-detail view. The plan is a visual guide, not an architectural blueprint.
- Additional saved rooms are preserved and remain available in Room Monitoring; they are identified separately rather than silently removed from the 15-room demonstration view.
- Dark Nexus Energy operations theme, collapsible desktop sidebar, and mobile navigation drawer.
- Live API connection state, headline consumption/cost/savings/emissions cards, room/floor status, and saved-reading trend charts with total and per-floor series.
- Normal, Warning, Critical, and neutral "No recent reading" states with configurable thresholds.
- Persistent room records, consumption history, settings, and acknowledgeable/resolvable alert history in SQLite.
- Alerts include values and threshold/baseline reasons; possible unusual use is never called confirmed wastage.
- Opt-in browser alarm generated by the Web Audio API; dedicated sound on/off, test, stop, and alert mute controls.
- Reversible Normal, sudden spike, sustained high-use, and after-hours demo scenarios, tagged in history.
- Floor, room, status, severity, search, and date filters; room details and dated manual readings with notes.
- Floor, room, historical snapshot, actual-versus-expected, alert frequency, and cost charts (Chart.js).
- Estimated room, floor, and building costs; the dashboard tariff editor persists through Settings, and reduction scenarios show estimated costs and potential savings.
- Daily run-rate, seven-day run-rate, and month-to-date carbon estimates use the configurable emissions factor and are explicitly identified as estimates.
- 10%, 20%, and 30% savings projections, configurable tariff and grid-emissions factor.
- Date-filtered CSV summaries containing floor comparisons, room readings, and alert history.
- Data-backed top room rankings and energy-saving inspection insights.
- Non-destructive demo reset restores baseline values while retaining reading and alert history.
- Parameterized database queries and validated JSON endpoints.

## Install and run in VS Code

Open this folder in VS Code, then run these commands in its terminal:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python app.py
```

If PowerShell blocks virtual-environment activation, run `.\.venv\Scripts\python.exe -m pip install -r requirements.txt`, then `.\.venv\Scripts\python.exe app.py`.

Open **http://127.0.0.1:5000** in your browser. The database is created or upgraded at `instance/electricity.db` on launch. Set `ELECTRICITY_DB` to use another SQLite file. The local demo runs without a login by default; do not expose the Flask development server to an untrusted network.

## Authentication and production deployment

Production mode requires a configured single administrator account and stable signing key. Never commit these values or paste them into source code. Store them in your deployment's secret manager. The administrator password must be at least 14 characters; the signing key must be at least 32 characters.

For a local PowerShell production-mode smoke test, install the requirements and set secrets in the current shell. Generate the signing key once and keep it in a password manager or secret store so it does not change on restart:

```powershell
$env:NEXUS_ENV = "production"
$env:NEXUS_SECRET_KEY = "<stable random value of at least 32 characters>"
$env:NEXUS_ADMIN_USERNAME = "<admin username>"
$env:NEXUS_ADMIN_PASSWORD = "<private password of at least 14 characters>"
.\.venv\Scripts\waitress-serve.exe --listen=127.0.0.1:5000 app:app
```

Open **https://your-domain/** through a TLS-terminating reverse proxy. For local smoke tests only, `http://127.0.0.1:5000` can be used, but production session cookies are marked Secure and therefore require HTTPS in a browser. Keep Waitress bound to localhost behind the TLS proxy; do not expose it directly to the internet. The app fails to start in production if required secrets are missing, and it disables Flask debug mode.

Production mode adds administrator login, an eight-hour signed session, HttpOnly/SameSite cookies, CSRF tokens for state-changing requests, response security headers, and no-store caching for authenticated responses. The health endpoint remains public and returns only service/database status. This is single-admin authentication, not multi-user authorization or an account recovery system. Configure login rate limiting at the reverse proxy. Keep the reverse proxy, TLS certificate, firewall, operating system, and secret storage secure; the app does not configure those infrastructure components.

## Test the red alert and alarm

1. Open the dashboard; seeded readings demonstrate Normal, Warning, and Critical rooms immediately.
2. Click **Sound Off** once to enable browser audio. Allow playback if your browser prompts; the enabled state is saved in Settings.
3. Click **Test Sound** to play a short generated tone sequence. Click **Stop Sound** to stop it before it finishes. **Alerts Muted** suppresses alert audio only; visual alerts remain visible.
4. Use **Try a reading scenario** for normal usage, a sudden spike, sustained high usage, or an after-hours event. Readings and alerts are marked SIMULATED and reversible. After-hours is a labeled demo event, not a conclusion inferred from a monthly reading.
5. Click **Stop simulation** to restore that room's previous reading; the simulated event remains acknowledged in history for demonstration transparency.
6. For a manual event instead, select a normal room and save a reading above its expected limit. The room turns red, a new alert appears, and enabled sound plays.
7. Re-saving a critical reading does not create a duplicate alert while the room remains Critical. Acknowledge alerts in **Alerts center**; resolve warning/critical alerts only after that room has a current reading in the normal range.
8. Use **Settings → Reset demo data** to restore baseline room values and default settings. Existing readings and alert history are retained.

Alert sounds only play for newly created critical events after sound has been enabled and browser audio has been activated by a click. Existing demo alerts remain visible without replaying the alarm on every dashboard refresh. A newly enabled setting may still require one click on **Test Sound** to satisfy browser autoplay restrictions.

The dashboard's daily-use card is an explicitly labeled month-to-date run-rate estimate. The application stores monthly cumulative readings, not real interval consumption. Chart dates show the latest saved reading snapshot per room for each date/period; they are not fabricated meter telemetry.

## Thresholds and cost

The default expected limit is 20% above each room's historical monthly average. The warning threshold defaults to 80% of that expected limit. A critical threshold can be configured below 100% for earlier alerts; any reading above 100% of the expected limit is Critical by default. A reading exactly at the limit is not considered to exceed it.

Estimated cost is current consumption × configured price per kWh. Potential savings are an estimate of the cost of consumption above expected limits; they are not a guaranteed bill reduction.

The analytics projection applies a selected 10%, 20%, or 30% reduction to the recent-room total; it is a scenario, not a prediction. Estimated carbon = recorded kWh × configured kg CO₂e/kWh factor (default 0.7); adjust the factor for your local grid. Rooms with no saved reading in 45 days show neutral "No recent reading" status and are excluded from current totals. Automated spike comparisons require at least three non-simulated readings. Sustained-high detection counts repeated snapshots, not continuous duration. Monthly cumulative readings and the lack of occupancy schedules prevent reliable automatic after-hours detection.

## API

All JSON endpoints use SQLite-backed data. Invalid values return a JSON `error` and an appropriate HTTP error status.

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/health` | Check app/database availability |
| GET | `/api/dashboard` | Summary, rooms, active alerts, and settings |
| GET | `/api/floors` | Floor groupings with consumption and estimated cost |
| GET | `/api/rooms?floor=1` | List rooms, optionally filtered by floor |
| GET | `/api/rooms/<room_id>` | Room metrics, history, and recent alerts |
| POST | `/api/rooms` | Add a room |
| PUT | `/api/rooms/<room_id>` | Update room information |
| POST | `/api/consumption` | Submit a reading and detect a new critical event |
| GET | `/api/consumption/history?room_id=1&start=2026-01-01&end=2026-12-31` | Query saved readings |
| GET | `/api/reports.csv?start=2026-10-01&end=2026-10-31` | Export summary, room readings, and alert history |
| POST | `/api/demo/simulate` | Create a tagged normal, spike, sustained, or after-hours scenario |
| POST | `/api/demo/simulation/stop` | Restore the previous reading and acknowledge the demo event |
| GET | `/api/alerts?severity=CRITICAL&floor=2&start=2026-01-01&end=2026-12-31` | Filter alert history |
| POST | `/api/alerts/<alert_id>/acknowledge` | Acknowledge an alert |
| POST | `/api/alerts/<alert_id>/resolve` | Resolve a warning/critical alert after its room returns to normal |
| GET | `/api/settings` | Read application settings |
| PUT | `/api/settings` | Update price, thresholds, and polling interval |
| POST | `/api/demo/reset` | Restore baseline readings without deleting history |

Example manual or future IoT reading request:

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:5000/api/consumption `
  -ContentType "application/json" `
  -Body '{"room_number":"203","consumption_kwh":165}'
```

A future meter integration can submit readings to this endpoint using `room_id` or `room_number` and `consumption_kwh`. Authenticate and secure the endpoint before connecting real devices.

## Limitations and future work

Readings are demo or manually submitted monthly totals; the frontend polls the Flask API and cannot make readings real-time unless a meter integration submits them. The daily run-rate is a simple month-to-date estimate, and cost/savings figures are estimates rather than billing guarantees. Authentication supports one administrator only; roles, account recovery, utility billing rules, and actual meter hardware are not included. Production still requires secure secret management, TLS/reverse-proxy configuration, firewall rules, backups, and operational monitoring. Future work could add multi-user roles, authenticated IoT ingestion, meter calibration, interval-reading aggregation, and configurable alert delivery.
